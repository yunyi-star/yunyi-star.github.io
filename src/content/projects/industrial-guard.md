## 做的是什么

一个面向实验环境的工控通信与防护原型，涉及上位机服务、PLC 侧状态逻辑以及主机侧防护工具。项目中的重要工作是把“有代码”推进到“可以检查两端是否理解了同一份数据”。

这里展示工程方法，不公开原型的实际协议、现场参数或可直接用于目标系统的操作步骤。

## 工程组成

| 方向 | 实现内容 |
| --- | --- |
| 通信适配 | 上位机读写接口、重连与重试分支、链路探测入口 |
| 两端对齐 | C# 与 PLC 侧逻辑的输入输出核对、自测与回环诊断 |
| 状态处理 | 等待、有效性判断、超时和异常状态的显式处理 |
| 防护原型 | 事件记录、白名单、临时规则管理与到期恢复 |
| 联调记录 | 从物理链路、网络连通到应用层逐层定位故障 |

## 两种“通信失败”，两条完全不同的排查路径

**第一种是链路根本没有建立。** 网卡状态记录显示持续断开，换线后才出现明确连接状态。后来还遇到端口有应答但协议握手不成立：真正运行的是另一项底层服务，预期的桥接组件并未就绪。因此，网络能连上和对端服务正确，必须分别检查。

**第二种是大多数帧正常、少量帧失败。** 旧流程平均耗时只有约 7–8 毫秒，但写入往返存在约 143 毫秒尖峰，最终提交可能跨过对端状态更新窗口。修复围绕块读、载荷与提交标记的顺序、写后回读、窗口预算与提交后状态核对展开，不再只盯平均值。

当恢复逻辑会让告警消退时，验收还需要持久失败计数和事件日志。开发报告记录了指定桥接环境中约 3 分钟、1800 帧的失败计数无新增；这个结果没有被扩写为真实设备或生产安全保证。

## 一个实际的调试方法

通信不通时，先确认观察层次：设备是否建立物理链路，双方地址与路由是否匹配，服务是否能连接，最后才检查数据布局和应用逻辑。每次只改变一个条件，并留下能区分原因的观测。

这个方法的价值在于缩短排障路径：应用层反复重试，不能修复物理链路故障；一侧自测通过，也不能证明两端的字节序、数据长度和更新顺序已经一致。

## 安全认识上的修正

校验和、消息认证和加密解决不同的问题。给校验和混入一个秘密值，不能直接得到可靠的消息认证；自定义运算能够在两端运行，也不构成密码学安全证明。
