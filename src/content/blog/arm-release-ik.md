物块已经被送到投放位置，吸盘也释放了，但机械臂接着把它扫飞。直觉上，这像是目标坐标没调好；实际检查动作过程，问题发生在**释放之后的脱离动作**。

这篇复盘根据 2026-08-20 的工程补丁与机械臂实现整理。代码片段省略日志与设备参数，保留修复的关键顺序。

## 最初的动作：末端后退一点，为什么腕部转了一大圈

旧方案在释放物块后，给末端一个很小的笛卡尔位移，再通过逆运动学求新的关节目标。任务的意图只是“让吸盘离开物块”，但一个很小的末端位移，并不保证求解器返回一组与当前关节角连续的解。

当时的代码注释记录了腕部约 240° 的回旋。这个动作出现在放气之后，所以视觉上就像“位置明明到了，东西还是被碰走”。只盯着最终落点继续改偏移，抓不到发生错误的那一段动作。

排查时真正要拆开的是：到达投放位姿、释放物块、脱离物块、回到初始姿态。把这四段分开观察，才能判断问题属于哪一个阶段。

## 修复：用关节空间表达这一次脱离

在当时的槽位姿态下，工程确认了第一关节朝回位方向的小幅转动能让吸盘离开物块，于是把这一步改为关节目标，不再重新求末端 IK。实际实现对第一关节增加 5°，其余关节保持当前值。

整理后的核心逻辑是：

```python
pump_off()
wait_until_settled()
joints = get_current_joint_values()
joints[0] += release_delta
set_joint_value_target(joints)
go(wait=True)
```

这里的 5° 是那组姿态下确认的脱离动作，不是任意机械臂都可以照抄的参数。修复的关键是：**这次只需要一个已知关节的小动作，就不要让求解器重新选择整套关节构型。**

## 第二个问题：函数返回成功，设备却还在动

修正 IK 后，工程还发现了另一个时序问题：驱动发出 G-code 后就可能报告成功，机械臂实际尚未停稳。

如果这时立即读取关节角并计算脱离动作，读到的是运动途中的角度。后续指令就可能把机械臂停在中间位置，表现仍然像投放点偏了。回位时还会遇到规划起点与实际状态不一致，出现 `start point deviates` 或动作中止。

因此，代码补上了两类检查：

- 规划前等待有效的关节反馈，避免拿断流或无效状态作为起点。
- 在关键动作后连续采样关节角，检查多次采样是否保持在容差内，再继续下一段动作。

这次真正区分开的，是“命令已经发出”“驱动已经返回”和“机械臂已经停止”。它们不是同一个事件。

当前实现也留有一处需要继续改进的地方：等待函数超时会返回失败，但投放路径没有据此强制中止。因此这段补丁增加了状态观察，却还不能被描述为严格的“未停稳就绝不继续”互锁。

## 任务不再无限等待：看门狗解决了什么，又没解决什么

同一轮整理还给机械臂任务增加了总时限、标记数据新鲜度检查，以及取消、停止轨迹和复位的路径。等待标记时，不只检查缓存里有没有标记，还检查时间戳，避免把旧帧当成当前观测。

但不能把这个补丁写成“并发问题已经彻底解决”：现有调度器在超时后会启动后台取消与复位，同时允许主任务继续；线程等待也有上限。**主线程不再卡住，不等于旧动作已经确定停止。** 后续更严格的设计应让设备所有权和恢复完成确认显式化，避免下一项任务与后台复位争用机械臂。

## 这次留下来的排查方法

1. 不把“东西最终落错了”直接归结为坐标错；先确定是哪段动作改变了结果。
2. 检查小幅末端位移对应的关节变化，尤其是求解分支是否跳变。
3. 不把驱动返回值当作物理完成信号，核对实际反馈。
4. 超时后检查旧任务是否真正退出，而不只检查调度器是否继续打印日志。

实现依据：`place_tag_block()`、`_wait_settled()`、`go_home()` 与任务调度器中的取消和看门狗路径。这是对已有修复的复盘，不是本次重新进行的机械臂实测。
