这是我在做 ISCC 2026 加密模块时踩的第一个坑，也是我整个项目里最想写下来的一次判断。

## 第一版设计

任务要求做"守狗挑战-应答"：PLC 侧每 100ms 生成一个随机 `Challenge`，上位机算出 `Response` 写回，PLC 校验通过才放行受保护的顺控。

我第一版的方案是：

```
Response = CRC32(KEY ⊕ Challenge ⊕ SECRET)
```

设计的时候我觉得这挺合理：三个东西混在一起异或，再过一层 CRC32，攻方看不到明文，看不到 KEY，也看不到 SECRET。KEY 和 SECRET 是赛方给的、公司内部约定的，只有我这边知道。

**写完我盯着这个公式看了很久，觉得哪里不对，但说不出来。**

## 真正的死因

后来我把它当数学问题重新算了一遍。

CRC32 不是一个"黑盒函数"，它有两条公开性质：

1. **它是仿射的**：对 GF(2) 上的向量运算，`CRC(a) ⊕ CRC(b) = CRC(a ⊕ b) ⊕ 常量`
2. **它是可逆的**：扣掉那个常量，剩下的线性部分是非奇异的，逆矩阵是存在的，而且**逆运算是公开的**——任何人都能算

把这两条套到我的公式上。记 `K = KEY ⊕ SECRET`：

```
f(x) = CRC32(x ⊕ K)
     = CRC32(x) ⊕ CRC32(K)          ← 仿射展开
     = L(x) ⊕ [L(K) ⊕ c]
       └─────┘   └──────┘
        公开可算    K'
```

`K' = L(K) ⊕ c` 是一个**固定的等效密钥**。于是：

- 攻击者观测到任意**一次**合法交互，拿到 `(Challenge, Response)`
- 因为 `L` 可逆，`K' = Response ⊕ L(Challenge)`，他就把"等效密钥"算出来了
- 之后他可以**自选**任意 `Challenge'`，算出对应的 `Response'`，写回 DB
- PLC 校验永远通过

**不需要两组。也不需要解方程。一组就够了。**

致命的地方不是"线性"，是"**可逆，而且逆运算公开**"。

## 我当时错在哪

我把"用了密钥"当成了"密钥被保护"。

这是个偷懒的等式。我以为异或 + CRC32 构成了混淆，实际上异或只是把 KEY 挪了个位置，而 CRC32 是一个**公开的双射**——它没有隐藏任何东西，它只是重新排列了一下。攻击者不需要破解 CRC32，CRC32 本来就不是用来保密的，它是用来**检错**的。

> 用检错算法去做保密，方向就错了。

真正的分界线在这里：

| | 结构 | 攻击者知道结构吗 | 拿到一次观测后 |
|---|---|---|---|
| CRC32 方案 | 公开标准 | **是**，逆运算也是公开的 | 直接反解等效密钥 → 任意伪造 |
| 自研 ARX 方案 | 自定义轮函数 | 否，且密钥未知 | 无法反解 |

所以安全性的来源不是"我用了密钥"这个**形式**，而是"**密钥未知 + 结构未知**"这个**状态**。

## 换掉之后

我最后改成了自研的 ARX 轮函数（加法 / 循环移位 / 异或混合，多轮迭代）。

选它的理由很具体，不是"看起来更高级"：

- **非线性**：加法和循环移位混着来，破坏仿射结构，不再有上面那个反解路径
- **无查表、无 S 盒**：在 PLC 侧用 SCL 能直接算，不需要额外搬一张几百字节的表进受限设备
- **跨语言可对齐**：C# 和 SCL 两侧必须算出**逐位相同**的结果，所以运算顺序、模运算回绕行为都要写成规范；SCL 那边还要关掉 IEC 检查才能拿到预期的 32 位回绕语义
- **双向成本对称**：PC 和 PLC 算的是同一个东西，调试时能互相对拍

### 顺带一个坑：帧号必须参与 MAC

跨实现对齐之后又踩了一次。第一次我把 `Response` 设计成只跟 `Challenge` 有关，联调时发现同一台机器在两个不同帧上给出了相同的应答——因为 `Challenge` 撞了。

加严之后 `Counter` 也进了 MAC 输入，帧号不同则应答必不同。**当时写进文档的备注是「禁止跨帧复用」，后来变成一条硬规则。**

这类问题不接真机永远发现不了，而宿舍里没有硬件——所以我把能做的部分尽量搬到能做的机器上：上位机全量开发 + 自测，PLC 侧用 PLCSIM 跑真协议栈对拍。

## 复盘

这件事之后我改了一个习惯：**写完方案先问"它是怎么被破的"，而不是"它是不是看起来很安全"。**

前者能推出可执行的结论，后者只能推出感觉。

还有一个更早的教训。我最初判断"CRC32 方案应该没问题"的时候，理由是"我看不懂它怎么被破"。**看不懂 ≠ 安全**，在安全设计里这句话反过来更危险。

后来我做检测器的时候又用过一次这个思路：闭端口上的 SYN 会被内核 RST 掉，根本不进连接表——所以任何基于连接表的检测器对端口扫描都有物理盲区。发现之后补了 20 个高位端口的假监听。这两件事本质一样：**先搞清楚"我的观测点到底能看到什么"。**
